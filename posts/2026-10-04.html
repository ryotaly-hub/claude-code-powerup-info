注意点

Bash の deny/ask ルールが、環境変数プレフィックス付きコマンドで無視されていた不具合を修正（v2.1.289）

サンドボックスの自動許可が効いている状態で、TZ="$HOME" rm -rf build のように環境変数プレフィックスを前に付けたコマンドだと、本来かかるはずの Bash deny/ask ルールがそのコマンドを見逃していた。素のコマンド文字列に対するルール一致を前提にしていたチームの permission 設定では、この書き方で意図せず危険なコマンドが素通りしていた可能性がある。あわせて、裸の変数代入がコマンドの前に来るケースでも deny/ask ルールがスキップされる不具合も修正された。

つまりこう使う

  • settings.json などで Bash の deny/ask ルールを運用しているなら、v2.1.289 に上げて「環境変数プレフィックス付きコマンドが素通りしていないか」を再確認する
  • 特に rm -rf や git push --force など破壊的コマンドを deny している場合は、VAR=val <command> 形式での回避余地がなくなったことを押さえておく
  • Claude Code Changelog
注意点

`Read` の deny ルールが、シンボリックリンク経由のファイルに効いていなかった不具合を修正（v2.1.289）

@ でメンションしたファイル、変更されたファイル、IDE で選択したファイルがシンボリックリンクだった場合、Read の deny ルールがリンク先の実体に対して適用されていなかった。機密ファイルへの直接パスは deny していても、そこへのシンボリックリンクを経由すると読めてしまう状態だったことになる。

つまりこう使う

  • .env や秘密情報を含むファイルへのアクセスを Read の deny ルールで止めているプロジェクトは、v2.1.289 への更新後に意図通り遮断されるか確認する
  • シンボリックリンクをリポジトリ内に置いている場合、リンク元・リンク先どちらのパスで deny ルールを書いていたかを見直す
  • Claude Code Changelog
エコシステム

今週追加された Claude Mods が、アップグレード後の最初のセッションで読み込まれない不具合を修正（v2.1.289）

v2.1.287 で追加されたばかりの Claude Mods（プラグインがより深い挙動を変更できる仕組み）で、Claude Code をアップグレードした直後の最初のセッションではインストール済みの mod が読み込まれないという不具合があった。2回目以降のセッションでは正常に読み込まれていたが、アップグレード直後に mod が動かないように見えて戸惑うケースがあった。

つまりこう使う

  • /plugin enable cc-plugin-you-should-know@builtin などで mod を使っている場合、アップグレード直後に mod が動いていないように見えたら、v2.1.289 への更新とセッションの再起動を試す
  • Claude Code Changelog
Tips

短いコード片で `<script>` タグの閉じ忘れや `${` の深いネストがあるとターミナルが固まる不具合を修正（v2.1.289）

Claude の応答に含まれる短いコードブロックに、閉じていない <script> タグがいくつも入っていたり、${ によるテンプレートリテラルのネストが深かったりすると、ターミナルの描画が固まることがあった。フロントエンドのコードやテンプレート文字列を多用するコードをレビューしてもらっているときに発生しやすかった不具合。公開済みアーティファクトのページが同じパターンで固まる・クラッシュする不具合も同時に修正されている。

つまりこう使う

  • レビュー中にターミナルが固まったら、再現コードの <script> タグや ${ のネストを疑う前に、まず v2.1.289 に更新してから再実行してみる
  • Claude Code Changelog
新機能

チームエージェント向けに `agent.spawn` と `$.agent.list()` のアイドル/待機状態が追加（v2.1.289）

プラグイン・mod 開発者向けに、teammate（チームエージェント）を生成する agent.spawn が追加された。あわせて、1つのエージェントに対して複数のプラグインフックイベントをまたいで同じ agent id が振られるようになり、$.agent.list() では idle（待機中）・waiting（応答待ち）の状態が取得できるようになった。複数エージェントの状態を監視・調整する mod を作る際に、どのエージェントが何をしているかを正確に追いやすくなる。

つまりこう使う

  • 複数エージェントを束ねる mod や plugin を自作しているなら、agent.spawn でチームエージェントを立ち上げ、$.agent.list() の idle/waiting 状態でハンドオフのタイミングを判定する
  • フックイベント間でエージェントを追跡するコードを書いている場合、agent id が一貫して振られるようになった前提で実装を見直せる
